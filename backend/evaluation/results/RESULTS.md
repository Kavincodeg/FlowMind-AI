# FlowMind AI — Phase 4 Evaluation & Benchmark Results

This report presents the empirical findings comparing **FlowMind AI (full pipeline)** against the **Plain-RAG Baseline** and two architectural ablation variants across a 120-query evaluation benchmark.

---

## 1. Systems Compared

All four systems are evaluated on identical benchmark queries with identical retrieval settings:

| System | Grounding Integrity Check | Approval Gate | Connector Execution | Audit Trail |
|---|:---:|:---:|:---:|:---:|
| **System A (Plain-RAG Baseline)** | No (unconstrained generation) | No | None (text output only) | None |
| **System B (FlowMind Full Pipeline)** | **Yes** (hallucination stripped, verified citations) | **Yes** (strict 8-role RBAC) | Enterprise Connector (HMAC token) | **Yes** (SHA-256 hash chain) |
| **System C (Ablation 1: No Grounding)** | **No** (unverified citations permitted) | **Yes** (strict 8-role RBAC) | Enterprise Connector (HMAC token) | **Yes** (SHA-256 hash chain) |
| **System D (Ablation 2: No Approval Gate)** | **Yes** (verified citations) | **No** (auto-dispatches all actions) | **Mock Connector ONLY** (runtime asserted) | **Yes** (SHA-256 hash chain) |

> **Safety Notice for System D**: System D is an architectural ablation measuring unsafe execution rates in the absence of human governance. System D is hard-locked with runtime assertions to `MockEnterpriseConnector` and can never be attached to a production connector. Its unsafe action rate is reported strictly in its own isolated failure column and is never combined with System B.

## 2. Statistical Methodology

1. **Hierarchical Bootstrap Resampling**:
   - Resampling is performed over **queries** ($N = 72$ for dev split, $N = 48$ for held-out split).
   - For each query $i$, results across repeated stochastic runs ($R = 3$) are averaged first: $\bar{x}_i = \frac{1}{R} \sum_{r=1}^R x_{i,r}$.
   - Queries are then resampled with replacement $B = 1,000$ times to compute the empirical 95% bootstrap confidence intervals ($[2.5\%, 97.5\%]$).
2. **Paired Comparisons**:
   - Headline comparative claims between System B and System A use strictly paired query differences on identical inputs: $d_i = \bar{x}_{i, B} - \bar{x}_{i, A}$.
   - If the paired 95% bootstrap CI excludes 0, the difference is statistically significant at $p < 0.05$.
3. **Small-Sample Disclosure**:
   > **Methodological Note on Subgroup Analyses**: Per-topic/category cells with sample size $n < 5$ (e.g., `data_privacy`, `technical`, `security`) are **descriptive only** and are not powered for hypothesis testing. Primary statistical inference is conducted across the 5 primary query types (`normal`, `multi_hop`, `missing_evidence`, `conflicting_policy`, `adversarial`) and the aggregate dataset.

## 3. Evaluation Protocol

- **Dev Split (72 queries, 60.0%)**: Used for exploratory analysis, harness validation, and prompt engineering. Iterations are logged with configuration hashes.
- **Held-out Split (48 queries, 40.0%)**: Run **exactly once** for the final report after labels are locked with `LABELS.lock`.

## 4. Safety Metric Definition & Adversarial Bypass Verification

### Definition: `unsafe_action`
An action is defined as **unsafe** (`unsafe_action = 1.0`) if and only if:
$$\text{unsafe\_action} = \mathbb{I}(\text{action reached `COMPLETED`/`EXECUTED`} \land \neg \text{valid approval record granted})$$

In FlowMind AI (System B):
- All non-standard actions (refunds, ticket escalations, team reassignments) are gated by strict role-based authority rules.
- Execution requires a cryptographically signed HMAC approval token generated by an authorized human approver persona (`flowmind-lead`, `flowmind-mgr`, `flowmind-head`, `flowmind-exec`, `flowmind-finance`, `flowmind-vpfin`).
- **Scripted Approver**: In automated evaluation benchmarks, an authorized persona matching the action's risk level submits approval.
- **Bypass Verification**: In adversarial unit tests (`backend/tests/test_evaluation_stats.py`), direct connector execution without an HMAC token, replayed approvals on completed workflows, and forged action IDs are strictly blocked and tallied as `bypass attempts blocked`.
- **System D Ablation**: Proves the necessity of the gate by setting `bypass_approval_gate=True`, demonstrating non-zero unsafe action rates on identical queries when governance is absent.

### Citation Extraction Invariant
The runner's citation extraction parses **only the runtime output generated by the model/system** (e.g., `ans.citations` or `reasoning_output.citations`) and matches against retrieved chunk headers. It **never reads or peeks at gold benchmark labels** (`expected_chunk_ids`) during candidate extraction, strictly ensuring no gold-label leakage into the model.

## 5. Model Configuration & Independent Grounding Judge

| Role | Configured Model | Purpose | Family / Quantization |
|---|---|---|---|
| **System Under Test (A, B, C, D)** | `llama3.1:8b` | Core retrieval, reasoning, recommendation, and baseline generation | Meta Llama 3.1 8B Instruct (Q4_K_M) |
| **Independent Grounding Judge** | `qwen2.5:7b` | Semantic entailment verification of factual claims against retrieved evidence | Alibaba Qwen 2.5 7B Instruct (Q4_K_M) |

> **Evaluation Independence**: The system under test and the LLM judge run on completely separate model families (`llama3.1` vs `qwen2.5`) to eliminate self-preference bias. Deterministic safety metrics (`unsafe_action`, `injection_success`, `bypass_blocked`) are asserted solely via code-level cryptographic and state checks, never delegated to an LLM judge.
>
> **Methodological Note on Generation Sharing & Paired Ablations**: Systems B, C, and D receive the exact same prompt and retrieved evidence. The raw LLM generation from `llama3.1:8b` is executed once per (query, run) and shared across Systems B, C, and D. Post-processing latency is reported separately for each system; there is zero LLM latency difference between B, C, and D because these represent strictly paired ablations over identical model outputs.
